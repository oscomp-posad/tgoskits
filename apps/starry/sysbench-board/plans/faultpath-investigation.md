## fault-path-cost
**findings:**
- FAULT-AROUND EXISTS (corrects the scout): the anon write first-touch does NOT map one page per fault. AddrSpace::handle_page_fault builds a 32-page forward readahead window (os/StarryOS/kernel/src/mm/aspace/mod.rs:543 READAHEAD_PAGES=32, window computed :541-548) and calls backend.populate once for the whole window (:549-554). CowBackend::populate walks every page in the window and, for anonymous (file.is_none), calls alloc_new_at + i+=1 per page (cow.rs:365-368). So ~1 fault per 32 pages (~2x fewer faults than Linux's 16-page fault-around). The ~11x is PER-PAGE overhead, not fault count.
- Entry/serialization: the kernel #[page_fault_handler] takes the per-process address-space lock and holds it across the ENTIRE 32-page populate: access.rs:368 `aspace_arc.lock().handle_page_fault(...)`. Lock is a blocking sleeping Mutex (axsync/src/mutex.rs:236 lock_api::Mutex over RawMutex). Single-thread memset doesn't contend, but any multi-threaded faulting in the same process fully serializes here.
- PER-PAGE STEP 1 (page-table map) — cheap: pt.cursor().map -> memory/page_table_multiarch/src/bits64.rs:405-421, one 4-level get_entry_mut_or_create walk + one PTE store + push(vaddr). Amortized ~0.3us. Not dominant.
- PER-PAGE STEP 2 (frame alloc) — GLOBAL LOCK x2, not per-CPU: alloc_new_frame (cow.rs:112-116) -> alloc_frame (backend/mod.rs:34-48) -> global_allocator().alloc_pages(1,4096,VirtMem). In buddy_slab.rs:193-223 this takes the GLOBAL buddy lock `self.inner.lock()` (:199) AND a second global `self.usages.lock()` (:221) every call. Page granular allocation bypasses the per-CPU slab (per-CPU slabs at buddy_slab.rs:30-98 serve only small byte allocs). So 2 global SpinNoIrq (IRQ save/restore + atomics) per page, a hard cross-core serialization point.
- PER-PAGE STEP 3 (global refcount table) — HEAVIEST Linux-vs-Starry differentiator: alloc_new_frame also calls FRAME_TABLE.lock().init_frame(frame). FRAME_TABLE is ONE global SpinNoIrq<BTreeMap> (cow.rs:79). init_frame (cow.rs:59-68) does `Arc::new(SpinNoIrq::new(FrameRefCnt(1)))` (a heap allocation) plus a BTreeMap insert (O(log N), N grows to 65536 for 256MB, allocates tree nodes) — all under the single global lock. Linux uses an O(1) per-page struct-page refcount with no global lock and no tree/heap-alloc per page. This alone adds ~1-3us/page of alloc traffic + global serialization Linux never pays.
- PER-PAGE STEP 4 (zeroing) — generic memset, NO DC ZVA: alloc_frame zeroes via core::ptr::write_bytes(vaddr,0,4096) (backend/mod.rs:43), which lowers to compiler_builtins memset (a word-store loop). No aarch64 DC ZVA / clear_page path exists in the tree (grep found only a userspace libc memset). Linux arm64 clear_page uses `dc zva` (zeroes a cache-line group per instruction, avoids read-for-ownership) — roughly 3-5x faster page clear. Zeroing is through the kernel linear map, so the page is also written a second time later by the user memset (unavoidable, same as Linux).
- PER-PAGE STEP 5 (TLB) — UNNECESSARY broadcast invalidate per page, top-tier cost: map() pushes each vaddr into the cursor's flusher (bits64.rs:419); SMALL_FLUSH_THRESHOLD=32 (lib.rs:166) exactly equals the readahead window, so all 32 stay in the Array (never degrade to a single Full flush). On cursor Drop (bits64.rs:665-671 -> flush :648-662) it emits one M::flush_tlb(Some(vaddr)) per page = aarch64.rs:31 `tlbi vaae1is; dsb sy; isb` — an INNER-SHAREABLE (broadcast to all 8 RK3588 cores) invalidate followed by a full-system dsb sy + isb, PER PAGE. For a freshly-mapped previously-unused PTE the architecture requires NO TLB maintenance (no stale entry to evict; break-before-make only applies to changing a valid entry). So ~65536 broadcast TLBI+DSB SY+ISB sequences for 256MB are pure waste. axmm's own alloc backend even documents this (os/arceos/modules/axmm/src/backend/alloc.rs:60 'TLB flush on map is unnecessary, as there are no outdated mappings'), but the StarryOS cow populate path does not skip it.
- Area lookup is NOT a factor: self.areas.find (memory_set/src/set.rs:54-57) is an O(log n) BTreeMap range query done ONCE per fault (~2048 times for 256MB), negligible vs 65536 pages of per-page work.
- Net per-page picture (~15us/page Starry vs ~1.3us/page Linux): dominant excess = (5) unnecessary per-page broadcast TLBI+dsb sy + (3) global FRAME_TABLE Arc-alloc+BTreeMap-insert under one global lock + (2) global buddy+usages locks + (4) non-DC-ZVA memset. Steps 3/2/5 are pure Starry-only overhead; step 4 is 3-5x heavier than Linux.

**exact_code:**

**present:**
- 32-page anonymous+file readahead/fault-around window in AddrSpace::handle_page_fault (mm/aspace/mod.rs:527-575, READAHEAD_PAGES=32 :543)
- Batched file-backed readahead via single read_at run (CowBackend::alloc_file_run cow.rs:165-207) — already optimizes file mappings; anon uses per-page alloc_new_at
- Cursor-batched TLB flusher with Array/Full modes (page_table_multiarch bits64.rs:380-394, 648-662) — but threshold==window so it flushes per-page not once
- Per-CPU slab allocator for small byte allocs (buddy_slab.rs:30-110) — NOT used by page allocation
- Global CoW frame refcount table FRAME_TABLE (cow.rs:79) shared across all processes

**gaps:**
- Magnitudes are from static reading + architectural reasoning, NOT profiled. Need per-step measurement on RK3588 (e.g. cycle counters around alloc_pages / init_frame / write_bytes / cursor.flush) to confirm the ranking; the harness firsttouch_s / sysbench-@1KB rungs give end-to-end deltas but not per-step attribution.
- Did not confirm whether the board perf build enables any allocator contention beyond single-thread; sysbench memory @1KB is single-threaded so the aspace-Mutex and global-lock contention costs are latency (IRQ save/restore + atomics), not spin contention — multi-thread scaling impact is inferred, not measured.
- memtrack/tracking feature (ax-alloc/tracking, StarryOS/kernel/Cargo.toml:23) captures a backtrace per allocation (buddy_slab.rs:423-441); assumed OFF for perf builds but not verified in the board profile config — if ever on, it would dwarf everything.
- Did not measure how often the 32-page window is clamped by area.end() near the 128MB region tail (rare; not material).
- compiler_builtins memset behavior on this target assumed to be a word-store loop; not disassembled to confirm it isn't already using a wide/nontemporal variant.

**hazards:**
- Skipping the TLB flush for fresh maps is correct ONLY for previously-unused PTEs (the anon-first-touch map() case). The same populate path also runs handle_cow_fault (cow.rs:209-245) doing pt.protect/pt.remap on post-fork shared pages, which DO require flushing — any 'skip flush on populate' change must distinguish fresh map() from remap/protect, or restrict the skip to the Err(NotMapped)->alloc_new_at branch.
- FRAME_TABLE is load-bearing for CoW correctness (fork refcounts, cow.rs:396-408); replacing the per-page Arc+BTreeMap with a flat per-frame refcount array must preserve the drop_frame/dealloc ordering race guard noted at cow.rs:31-37.
- DC ZVA needs the DCZID_EL0 block size checked at runtime (typically 64B on RK3588) and the target page cacheable in the linear map; a naive dc zva loop with wrong block size corrupts adjacent memory.
- Widening the batched flusher (raising SMALL_FLUSH_THRESHOLD or forcing a single Full flush) trades per-page tlbi for one vmalle1 broadcast — fine for large fresh populates but a full-ASID flush is costlier than N small ones for tiny faults; make it conditional on run length.

**recommendation:** "The ~11x is per-page overhead, and fault-around already exists (32 pages), so attack the per-page work in this priority order. (1) Stop flushing the TLB for freshly-mapped pages: in the anon Err(NotMapped)->alloc_new_at branch (cow.rs:366) the PTE was is_unused, so no TLB maintenance is architecturally needed — skip cursor.push for fresh map()s (or add a map_no_flush) so the cursor-drop flush (bits64.rs:668) emits nothing. Removes ~65536 broadcast `tlbi vaae1is; dsb sy; isb` for 256MB. (2) Replace the global FRAME_TABLE Arc<SpinNoIrq>+BTreeMap (cow.rs:59-79) with a flat per-physical-frame refcount (u8/atomic array indexed by PFN), eliminating one global lock + one heap Arc alloc + one O(log N) tree insert per page. (3) Make page allocation batch/per-CPU: add a bulk alloc_pages(N) that takes the global buddy lock once for the whole 32-page window instead of 32x (buddy_slab.rs:199,221), and/or a per-CPU page free-list; also lift the second usages.lock() out of the hot path. (4) Add an aarch64 DC ZVA clear_page and use it in alloc_frame (backend/mod.rs:43) instead of generic write_bytes memset (~3-5x faster zeroing). (5) Lower-priority: consider dropping the per-process aspace Mutex to a finer scope / not holding it across the whole populate to unblock multi-threaded fault scaling. Verify each via the harness: firsttouch_s toward 0.086s and sysbench memory @1KB rising from 42 MiB/s. Expect (1)+(2) to recover the bulk of the gap; (3)+(4) close the remainder and fix multi-core scaling."

## Fault-around for anonymous first-touch demand paging (StarryOS mm on ArceOS)
**findings:**
- CONFIRMED root cause: AddrSpace::handle_page_fault populates exactly ONE page per fault. os/StarryOS/kernel/src/mm/aspace/mod.rs:587-622 builds a single-page range `VirtAddrRange::from_start_size(vaddr.align_down(page_size), page_size as _)` and calls `area.backend().populate(range, flags, access_flags, Some(&self.rss), &mut self.pt.cursor())`. There is no fault-around and no huge-page fallback, so a 256 MB memset takes 65,536 separate faults.
- The backend already populates a MULTI-page range in one call — fault-around needs NO new backend code, only a wider range. CowBackend::populate (os/StarryOS/kernel/src/mm/aspace/backend/cow.rs:508-560) does `pages_in(range)` -> iterates every page -> for each NotMapped anonymous page calls `alloc_new_at` (alloc zeroed frame + pt.map + RSS charge). It cleanly handles an N-page range today; it is only ever *given* a 1-page range by handle_page_fault. The eager populate_area() path (mod.rs:218-264) already drives this backend with multi-page ranges, proving sub-range population is safe.
- A MemoryArea is exactly one contiguous VMA with uniform flags and a single backend (memory/memory_set/src/area.rs:12-17; MemorySet::find returns the single area containing the addr, set.rs:54-57). So clamping a fault-around window to `area.va_range()` inherently prevents crossing into holes (no area), guard/PROT_NONE pages (separate area with different flags), or a different backend. area.va_range()/start()/end()/flags()/backend() are all available (area.rs:52-85).
- Anonymous vs file distinction is available: anon private mmap = `Backend::Cow` with file=None (`CowBackend::is_anonymous()`, cow.rs:150; constructed by Backend::new_alloc, cow.rs:640). discard_range already pattern-matches `Backend::Cow(c) if c.is_anonymous()` (mod.rs:281), so the same guard works in the fault handler.
- For anonymous pages the PTE flags are ALWAYS the full VMA flags regardless of read/write access: pte_flags_for_fault_in returns vma_flags unchanged when file.is_none() (cow.rs:192-202). Consequence: a NotMapped anon page is mapped writable+zeroed even on a READ fault, so a fault-around window populated with a READ access-mask still resolves a WRITE fault on a NotMapped page — this is what makes a safe read-masked window viable.
- The whole fault is served under the per-process aspace Mutex held across the entire handler (access.rs:294 `aspace_arc.lock().handle_page_fault(...)`), and each fault re-runs: trap entry, current()/thread lookup, PAGE_FAULT_COUNT atomic, aspace lock, BTreeMap find (O(log n)), a heap Vec alloc inside `pages_in`, then per-page frame alloc + 4 KB zero + two locked BTreeMap inserts (FRAME_TABLE + RSS). Fault-around amortizes every item in that list except the irreducible per-page frame-alloc/zero/map over K pages.
- The harness metric is exactly this path: membw.c memsets two ~256 MB malloc buffers (glibc -> MAP_ANONYMOUS|MAP_PRIVATE) and reports firsttouch_s (harness/membw.c:59-64). Baseline snapshot: StarryOS firsttouch 0.80-1.30 s vs Linux 0.086-0.30 s; warm memcpy is fine (7.3 GB/s A76). So firsttouch_s and sysbench memory @1KB-block are the direct gauges, and PAGE_FAULT_COUNT (/proc/vmstat pgfault, access.rs:245) will show the fault-count drop directly.

**exact_code:**
- CURRENT single-page site — os/StarryOS/kernel/src/mm/aspace/mod.rs:594-601:
    let page_size = area.backend().page_size();
    let populate_result = area.backend().populate(
        VirtAddrRange::from_start_size(vaddr.align_down(page_size), page_size as _),
        flags, access_flags, Some(&self.rss), &mut self.pt.cursor());
- PROPOSED window computation to insert before the populate() call (Linux do_fault_around analog, clamped to the VMA). All operands stay page-aligned so pages_in() cannot error:

    let fault_page = vaddr.align_down(page_size);

    } else {
        VirtAddrRange::from_start_size(fault_page, ps)  // unchanged for file/linear/shared
    };
- CORRECTNESS-PRESERVING two-call variant (recommended over widening the single call): keep the existing call for the faulting page with the real access_flags, then best-effort fill the neighbours with a READ mask so present COW pages are counted-not-copied and only NotMapped anon pages are allocated:
    // 1) resolve faulting page exactly as today (real access_flags)
    // 2) if anon: let _ = area.backend().populate(window_range, flags, flags - MappingFlags::WRITE, Some(&self.rss), &mut self.pt.cursor());

**present:**
- Single-page fault servicing in AddrSpace::handle_page_fault (mm/aspace/mod.rs:587-622).
- Multi-page-capable backend populate already used by populate_area (mm/aspace/mod.rs:218-264) and by CowBackend::populate (backend/cow.rs:508-560).
- File-backed readahead batching already exists (alloc_file_run, cow.rs:299-344) — the anon side has no equivalent batching, which is the gap.
- Anonymous detection guard (CowBackend::is_anonymous, cow.rs:150) already used elsewhere (discard_range, mod.rs:281).
- PAGE_FAULT_COUNT instrumentation (access.rs:245-295) and the membw firsttouch harness (apps/starry/sysbench-board/harness/membw.c) for before/after verification.

**gaps:**
- No bulk frame allocation/zeroing: alloc_new_at/alloc_new_frame (cow.rs:233-295) allocate ONE 4 KB frame and zero 4 KB at a time. Even with fault-around the K per-page allocs + K zeroings remain the floor. The larger follow-on win is an anon batch path (contiguous alloc_pages(K) + one write_bytes(K*4K), still recording per-4K FRAME_TABLE/RSS entries for COW) — analogous to the existing file-side alloc_file_run readahead (cow.rs:299-344), which the anon side lacks.
- No huge pages / THP: /proc/meminfo HugePages_Total=0. Linux's 0.086 s for anon 256 MB is largely THP (2 MB pages = 512x fewer faults + far fewer PT writes), not fault-around (which in Linux is file-backed only). Fault-around narrows the gap; fully matching Linux likely needs 2 MB mappings for large anon areas — out of scope here but the bigger lever.
- Choice of window policy unverified on-board: FAULT_AROUND_PAGES=16 vs 8/32, and whether to fault-around on read faults too, should be swept with the harness (firsttouch_s + PAGE_FAULT_COUNT + RSS) rather than assumed.
- TLB/PT-cursor batching benefit is plausible but unconfirmed: each populate() uses one `self.pt.cursor()`, so a window is mapped under a single cursor (one flush batch on drop) vs one cursor per fault today. For NotMapped->mapped there should be no TLB invalidation needed at all (no stale entry), so treat batched-TLB as a minor/secondary benefit, not the main win — not yet measured.
- No unit test exercises multi-page anon populate from the fault handler; add a kernel test that faults one address in a >64 KiB anon area and asserts the whole clamped window became resident and PAGE_FAULT_COUNT rose by 1, plus a fork+write test asserting neighbours are NOT copied (laziness preserved).

**hazards:**
- COW over-copy after fork: if the widened window is populated with the real access_flags and access contains WRITE, CowBackend::populate's present-page branch calls handle_cow_fault (cow.rs:525-529) and will EAGERLY COPY up to 15 neighbouring forked read-only COW pages per single write fault — correct but breaks COW laziness and inflates memory. Mitigate by populating the window with a READ mask (flags - WRITE) so present pages hit the `page_flags.contains(access_flags)` satisfied branch instead of being copied; NotMapped anon pages still map writable because anon PTE flags = vma_flags regardless of access.
- Do NOT pass a READ mask over the SINGLE faulting page when it is a present read-only page (post-fork COW / file deferred-write): a READ mask won't copy it, the write stays unresolved, and the CPU re-faults forever. This is why the faulting page must be served with the true access_flags (single-page call) and only the *neighbours* get the read mask.
- RSS/memory inflation: fault-around eagerly charges frames the program may never touch. Bound it exactly like Linux (64 KiB window, clamped to VMA, never extend before area.start) and consider gating on a write/first-touch heuristic. Every pre-faulted page is a real 4 KB frame here (no shared zero page), so the window size is the memory-vs-fault-count knob.
- Borrow structure: the change must keep `area`'s last use at/before the populate() call so NLL ends the &self.areas borrow before the deferred `cb(self)` runs (the existing code at mod.rs:602-613 already relies on this). Reading area.va_range()/flags()/backend() before the call preserves it.
- Aggregate firsttouch will NOT drop the full 16x: per-page frame alloc + 4 KB zeroing + pt.map + FRAME_TABLE/RSS BTree inserts are irreducible with this design. Fault-around removes the *fixed* per-fault overhead (trap, aspace lock, find, Vec alloc, atomics), not the per-page work.

**recommendation:** Concrete change site: AddrSpace::handle_page_fault at os/StarryOS/kernel/src/mm/aspace/mod.rs:587-622. The backend already populates arbitrary multi-page ranges, so fault-around is purely a wider range computed in the fault handler — no backend rewrite. Implement it as TWO populate() calls to stay correct: (1) serve the faulting page exactly as today with the real access_flags (preserves COW/write/deferred-file semantics and guarantees n>=1); (2) only when `matches!(area.backend(), Backend::Cow(c) if c.is_anonymous())`, do a best-effort populate over a 64 KiB (FAULT_AROUND_PAGES=16) window aligned down like Linux `do_fault_around` (`addr & ~(bytes-1)`), clamped to `area.va_range()` (so it never crosses a hole, guard page, or different backend), passing a READ mask (`flags - MappingFlags::WRITE`) so present COW/forked pages are counted-not-copied while NotMapped anon pages are allocated+mapped writable (anon PTEs are always full vma_flags). Ignore the neighbour call's error/callback. Keep the single-page path for file/linear/shared backends unchanged. Expected effect on the measured sequential memset: PAGE_FAULT_COUNT (/proc/vmstat pgfault) and trap entries drop ~16x (one fault per aligned 64 KiB window; the other 15 pages are already resident), and firsttouch_s falls from ~0.8-1.3 s toward roughly ~0.15-0.30 s (Linux range) — realistically a ~3-5x firsttouch win, not 16x, because per-page frame-alloc+zero+map is irreducible. Verify with apps/starry/sysbench-board/harness/membw.c firsttouch_s and sysbench memory @1KB-block, and snapshot as a rung. Next lever after this (bigger, separate change): batch anon frame alloc+zero (mirror alloc_file_run) and/or 2 MB huge mappings for large anon areas.

## populate-madvise: MAP_POPULATE honoring, madvise prefault wiring, and first-touch PT/TLB batching (StarryOS mm on RK3588)
**findings:**
- MAP_POPULATE IS honored today (verified). A mmap with MAP_POPULATE prefaults the whole region at mmap-time via populate_area. This is NOT the gap.
- madvise(MADV_WILLNEED / MADV_POPULATE_READ / MADV_POPULATE_WRITE) is a SILENT NO-OP. sys_madvise accepts these advices as valid (mmap.rs:842-848) but the action match only handles DONTNEED/FREE/DONTNEED_LOCKED (discard_range); WILLNEED/POPULATE_* fall through and return Ok(0) doing nothing (mmap.rs:883-889). Linux MADV_POPULATE_WRITE is exactly 'prefault writable now' — the populate_area primitive to implement it already exists.
- The scout's 'one 4KB page per fault / no fault-around' hypothesis is WRONG for anonymous first-touch: the fault path populates 32 pages per fault (2048 faults for 256MB, not 65536). Correct this in the effort's model.
- The benchmarks do NOT exercise any of this: membw uses malloc(256MB) which glibc routes to a plain mmap(MAP_PRIVATE|MAP_ANONYMOUS) with NO MAP_POPULATE and no madvise; firsttouch_s times ONLY the two memsets (malloc/mmap happen before t0). So first-touch goes entirely through the demand-fault + 32-page-readahead path (apps/starry/sysbench-board/harness/membw.c:50-60).
- REAL first-touch cost driver found in the TLB layer: on the fault path every fresh (not-present -> present) anon page still calls cursor.push(vaddr) (bits64.rs:419), and because a 32-page window fills the ArrayVec to exactly 32 (no overflow to Full), the cursor Drop issues 32 individual per-VA flushes. On aarch64 each is a BROADCAST 'tlbi vaae1is; dsb sy; isb' (memory/page_table_multiarch/src/arch/aarch64.rs:31) — ~65536 broadcast TLBIs + full system barriers for a 256MB memset on an 8-core RK3588. This is unnecessary: aarch64 does not cache faulting/not-present translations, so a fresh map needs NO TLB maintenance (Linux set_pte does not flush).
- MAP_POPULATE already dodges that TLBI storm: it maps the whole region under ONE cursor, so after 33 pages the flusher overflows to Full and Drop issues a SINGLE local 'tlbi vmalle1' (aarch64.rs:34) for the entire region instead of 65536 broadcasts. So MAP_POPULATE/eager-populate is a genuine end-to-end win here (TLB traffic 65536 broadcast -> 1 local), not merely moving the timer boundary.
- Residual per-page cost (unchanged by populate vs fault) that keeps StarryOS above Linux's 0.086s: alloc_frame(zeroed=true) zeroes every 4KB (then memset re-writes it — a double write), plus a per-frame insert into the GLOBAL FRAME_TABLE BTreeMap under one SpinNoIrq (backend/mod.rs:34-48, backend/cow.rs:59-68,112-116). These belong to the 'frame-alloc / refcount' area, not populate-madvise, but they cap what this area can achieve alone.
- The whole fault window (populate + all TLBIs) runs under the per-process aspace Mutex (access.rs:368), so on SMP concurrent same-process faults serialize — relevant to multithreaded first-touch, not the single-thread benchmark.

**present:**
- MAP_POPULATE end-to-end: sys_mmap decodes MmapFlags::POPULATE and passes it to aspace.map(); AddrSpace::map() calls populate_area(start,size,flags) over the WHOLE mapping when populate=true (os/StarryOS/kernel/src/syscall/mm/mmap.rs:485-486, os/StarryOS/kernel/src/mm/aspace/mod.rs:181-183). Also honored on the Ion path (mmap.rs:304-305) and by plain mlock (mmap.rs:990).
- populate_area primitive exists and walks the region area-by-area, calling backend.populate() with a fresh page-table cursor per area (os/StarryOS/kernel/src/mm/aspace/mod.rs:190-232).
- Fault path ALREADY does fault-around: handle_page_fault populates a 32-page forward window (READAHEAD_PAGES=32) for 4K areas, one huge page otherwise (os/StarryOS/kernel/src/mm/aspace/mod.rs:543-548). CowBackend::populate maps every not-mapped anon page in that window via alloc_new_at (os/StarryOS/kernel/src/mm/aspace/backend/cow.rs:354-369).
- TLB batching infra exists: PageTable64Cursor accumulates flush requests in an ArrayVec (SMALL_FLUSH_THRESHOLD=32); overflow past 32 downgrades to a single Full flush; flush happens on cursor Drop (memory/page_table_multiarch/src/lib.rs:166-172, memory/page_table_multiarch/src/bits64.rs:380-421, 647-671).

**gaps:**
- No heuristic eager-populate for large anonymous mmaps: populate only fires on explicit MAP_POPULATE, which glibc malloc/sysbench never set, so the benchmark never benefits.
- madvise prefault (MADV_WILLNEED / MADV_POPULATE_READ / MADV_POPULATE_WRITE) unwired — a 1-site fix calling populate_area is missing.
- cursor.map() (fresh not-present->present) unnecessarily records a TLB flush (bits64.rs:419); there is no 'no-flush on fresh map' fast path, so the demand-fault first-touch path pays a broadcast-TLBI-per-page cost that Linux does not.
- No batched/range TLBI primitive is used per populated region on the fault path; the range is flushed as up to 32 individual broadcast per-VA ops rather than nothing (fresh maps) or one range op.

**hazards:**
- Eager-populate / MAP_POPULATE commits physical memory up front: a heuristic that auto-populates large anon mmaps will blow up RAM on sparse/overcommit mappings (V8's multi-GB PROT_NONE cage, large-but-mostly-untouched arenas). file.rs:349-350 already carries a comment that unbounded MAP_POPULATE over a sparse mapping exhausts RAM — same failure mode for anon. This is non-Linux behavior (Linux relies on fault-around + THP, not eager anon commit).
- firsttouch_s can be 'gamed': auto-populating inside malloc's mmap moves the cost before t0, so firsttouch_s drops without total program time improving (it can even worsen due to double alloc+zero then memset). Do not report an eager-populate firsttouch win as a throughput win without also measuring wall-clock of malloc+memset together.
- Skipping the flush on fresh map is correct on aarch64/riscv/x86 (invalid entries aren't cached) and is what Linux does, BUT bits64.rs is a SHARED component used by ArceOS/StarryOS/Axvisor across all four arches; the change needs SMP-correctness review and must remain scoped to the not-present->present case only (remap/protect/unmap MUST still flush).
- Anon populate pages are mapped writable directly using area flags, so the readahead pages beyond the faulting page do not take a second CoW fault — good — but any change to populate access-flag handling must preserve this or first-touch regresses into double-faults.

**recommendation:** Do NOT spend this area's effort on MAP_POPULATE (already correctly wired) as the primary lever. Ranked plan: (1) HIGHEST LEVERAGE, fixes both fault and populate paths and is what Linux does: stop issuing TLB maintenance on fresh not-present->present maps — gate the self.push(vaddr) in PageTable64Cursor::map (memory/page_table_multiarch/src/bits64.rs:405-421) so a brand-new mapping records no flush. This removes ~65536 broadcast 'tlbi vaae1is; dsb sy; isb' from a 256MB anon first-touch outright, no memory committed up front, no metric-gaming. Scope strictly to fresh maps; keep remap/protect/unmap flushing; SMP review required since it is a shared crate. (2) LOW-EFFORT CORRECTNESS/COMPAT: wire madvise MADV_POPULATE_WRITE/READ and MADV_WILLNEED in sys_madvise (os/StarryOS/kernel/src/syscall/mm/mmap.rs:883-889) to call aspace.populate_area(addr,len, WRITE-or-READ) — the primitive exists; ~5 lines; lets opt-in apps prefault and is Linux-accurate. (3) OPTIONAL, benchmark-facing, guarded: a heuristic eager-populate for large PRIVATE|ANONYMOUS mmaps in the anon arm of sys_mmap (mmap.rs:478-480/485-486) behind a size threshold and gated off for MAP_NORESERVE — but treat it as a benchmark aid, not a real win, because per-page alloc+zero+FRAME_TABLE cost is unchanged and it commits memory up front. On batching: PT writes are ALREADY batched (one cursor per region); the honest answer to 'single TLB flush over the populated range' is that the range should need ZERO flushes for fresh anon pages, which item (1) delivers. The residual gap to Linux's 0.086s (double-zeroing + global FRAME_TABLE BTreeMap under one lock, and absence of THP/huge pages) lives in other areas and caps what populate-madvise can achieve alone.

## hugepages-batch — transparent 2MB block mapping + first-touch fault batching for StarryOS anon memory on RK3588
**findings:**
- VERIFIED: every layer below the syscall already supports 2MB/1GB blocks end-to-end; nothing new is needed in the page-table, PTE, backend, or allocator layers. The gap is purely in *policy* (when to choose a huge/batched mapping) plus one missing correctness primitive (huge->4K split).
- PAGE TABLE (memory/page_table_multiarch/src/bits64.rs): PageTable64Cursor::map(vaddr, target, page_size, flags) installs a block descriptor directly via GenericPTE::new_page(target.align_down(page_size), flags, page_size.is_huge()) (bits64.rs:405-421). get_entry_mut_or_create returns the PMD entry for Size2M / PUD for Size1G (bits64.rs:269-277). map_region already has an allow_huge mode that opportunistically upgrades aligned runs (bits64.rs:491-539). PageSize::Size2M=0x20_0000/Size1G with is_huge() (lib.rs:130-156).
- AARCH64 PTE (memory/page_table_entry/src/arch/aarch64.rs:212-218): A64PTE::new_page sets a VMSAv8 Block descriptor (omits NON_BLOCK) when is_huge=true; is_huge()/query() decode it (257-260). RK3588 4KB granule => PMD block = exactly 2MB. Fully functional.
- STARRY BACKEND IS ALREADY PAGE-SIZE PARAMETERIZED (os/StarryOS/kernel/src/mm/aspace/backend/cow.rs): CowBackend carries `size: PageSize`; page_size() returns it (124-134,465-467). Fault-in maps at self.size (pt.map(vaddr, frame, self.size,..) cow.rs:287,335); COW copy and unmap all use self.size. So a 2MB-sized anon backend already services a whole 2MB per fault.
- FRAME ALLOC ALREADY DOES CONTIGUOUS+ALIGNED (backend/mod.rs:38-52): alloc_frame(zeroed, size) => global_allocator().alloc_pages(size/4K, size_as_align, VirtMem). For Size2M that is alloc_pages(512, 0x200000) — a natural order-9 buddy block. buddy-slab alloc_pages(num_pages, alignment) (axalloc/src/buddy_slab.rs:193-223) supports it and has a reclaim-retry loop; 2MB (order 9) is realistic, 1GB (order 18) will usually fail under fragmentation.
- FAULT HANDLER ALREADY ALIGNS TO BACKEND PAGE SIZE (aspace/mod.rs:587-601): handle_page_fault populates exactly VirtAddrRange::from_start_size(vaddr.align_down(page_size), page_size) where page_size = area.backend().page_size(). So making the anon backend Size2M automatically makes one fault install one 2MB block covering 512 pages. No fault-handler rewrite needed for the block case.
- THE HUGETLB PATH ALREADY EXISTS AND IS THE TEMPLATE (os/StarryOS/kernel/src/syscall/mm/mmap.rs): MAP_HUGETLB/MAP_HUGE_1GB select page_size=Size2M/Size1G (179-185); VA is 2MB-aligned via find_free_area(.., align=page_size) (269-283); length rounded to page_size; backend built with page_size (new_cow/new_alloc, 541-543). Transparent promotion = apply this same selection heuristically for large anon mmaps when MAP_HUGETLB is absent.
- BENCHMARK TARGET CONFIRMED: harness/membw.c does malloc(128MB) x2 then memset (lines 50,57-58). glibc routes >MMAP_THRESHOLD requests through anonymous mmap(MAP_PRIVATE|MAP_ANON) => Backend::new_alloc(start, Size4K, "") (mmap.rs:543). 256MB memset = 65,536 separate 4K faults today; with 2MB backing = 128 faults (512x fewer) + 128 TLB block entries instead of 65,536 — hits both firsttouch_s and the sysbench @1KB-block per-op number.
- ZEROING: alloc_frame zeros with core::ptr::write_bytes(vaddr,0,page_size) (backend/mod.rs:47). At 2MB this is one large LLVM memset instead of 512 small ones. DC ZVA is architecturally enabled for EL0 (DZE bit, components/axcpu/src/aarch64/init.rs:93) but there is NO hand-rolled DC-ZVA zeroing routine; kernel zeroing relies on the compiler memset. A DC-ZVA block-zero loop is a secondary lever (write-BW bound, ~3-7 GB/s already).
- A THP GATE ALREADY EXISTS: per-task PR_SET_THP_DISABLE is stored (os/StarryOS/kernel/src/task/mod.rs:717-1045, thp_disable AtomicU32) and /proc/meminfo advertises Hugepagesize: 2048 kB (pseudofs/proc.rs:152-153). So a promotion policy has a natural, Linux-compatible opt-out already wired.

**exact_code:**

**present:**
- page_table_multiarch: full Size2M/Size1G block map/unmap/query + allow_huge auto-upgrade (bits64.rs)
- aarch64 A64PTE block-descriptor encode/decode (page_table_entry/src/arch/aarch64.rs)
- PageSize-parameterized StarryOS Backend (CowBackend.size) with per-fault map at self.size (mm/aspace/backend/cow.rs)
- alloc_frame(zeroed,size) -> buddy alloc_pages(num,align) contiguous+aligned frames with reclaim retry (backend/mod.rs, axalloc/src/buddy_slab.rs)
- handle_page_fault populates a backend-page-sized aligned window automatically (mm/aspace/mod.rs:587-601)
- Working explicit hugetlb mmap path as the promotion template (syscall/mm/mmap.rs:179-185,269-283,541-543)
- PR_SET_THP_DISABLE per-task gate + /proc/meminfo Hugepagesize:2048kB already present (task/mod.rs, pseudofs/proc.rs)

**gaps:**
- NO huge->4K split primitive — this is THE blocker for transparently promoting ordinary anon areas. pages_in(range, self.size=2M) = DynPageIter::new which returns None unless start AND end are 2MB-aligned (memory/memory_addr/src/iter.rs:101-114). Any sub-2MB partial op therefore fails: CowBackend::unmap returns InvalidInput => MemorySet::unmap shrink/split => MappingError::BadState (memory_set/src/set.rs:205-231). CowBackend::split only asserts a 4K multiple (cow.rs:603-611) so it will mint a 2MB backend at a non-2MB-aligned start that is then unusable. PT unmap_region/protect_region assert page_size<=size and alignment (bits64.rs:561-562,608-609) so a 4K op inside a 2MB block panics or clears the whole block. Net: munmap/mprotect/mremap/madvise(DONTNEED) on a sub-range of a 2MB-backed area = error or panic. MAP_HUGETLB is safe only because userspace keeps everything 2MB-aligned.
- Single-size-per-area model can't express 2MB interior + 4KB edges. A MemoryArea has exactly one Backend with one page_size. glibc malloc(128MB) mmaps ~128MB+header at 4KB alignment, so the region is neither 2MB-based nor 2MB-multiple in general. Promotion must either (a) fault-time promote only fully-covered, 2MB-aligned windows, or (b) split the mmap into up to three areas (4K head / 2M body / 4K tail). Rounding a whole area up to 2MB like the hugetlb path over-allocates VA and corrupts /proc/*/maps sizes — unacceptable for transparent use.
- No fallback-to-4K when a 2MB frame is unavailable. alloc_frame(Size2M) currently just returns NoMemory if the buddy can't produce an order-9 block (backend/mod.rs:43-45). Transparent promotion must degrade gracefully to 4K per fault, not fail the fault.
- fork/COW at 2MB granularity is coarse: handle_cow_fault copies the entire self.size (2MB) and remaps at 2MB on the first write (cow.rs:374-392); a child that writes one byte pays a 2MB copy. FRAME_TABLE refcounts one entry per huge frame (cow.rs:55-66) with no sub-page refcount, so post-fork partial writes can't be handled without either whole-2MB copy or a split.
- No fault-around/batching even at 4KB: today each 4K fault is a full trap + aspace-lock acquire + area lookup + single-page populate (aspace/mod.rs:587-601, access.rs:247-294). The fixed per-fault overhead is paid 65,536 times for the 256MB memset. There is no multi-page batch primitive on the anon write path (CowBackend::populate loops, but handle_page_fault only ever hands it one page).
- madvise(MADV_DONTNEED) already silently mis-behaves for anon if promoted: discard_range aligns fragments to backend page (aspace/mod.rs:285-286), so a 4KB DONTNEED on a 2MB-backed area would no-op instead of zeroing 4KB (a semantic regression to watch for).

**hazards:**
- Panic/error on partial munmap/mprotect/mremap/madvise of a promoted 2MB anon area (DynPageIter None, PT assert page_size<=size). Must land huge->4K split before any transparent promotion, or restrict promotion to areas that can only be operated on whole.
- VA and RSS bloat: 2MB granularity inflates RSS for sparse touches; rounding whole areas to 2MB breaks /proc/*/maps and mmap return-length semantics.
- Buddy fragmentation over uptime silently defeats 2MB allocation unless alloc_frame falls back to 4K per-fault; 1GB promotion is effectively unusable on a fragmented heap.
- fork then partial write pays full 2MB COW copy (no sub-page refcount in FRAME_TABLE); can regress fork-heavy workloads.
- DC-ZVA zeroing is write-BW bound (~3-7 GB/s measured) — real but secondary; do not expect it to move firsttouch_s much once fault count drops 512x.
- Concurrency: handle_page_fault holds the whole aspace Mutex; batching more work per fault lengthens the critical section — fine for single-thread membw, watch multi-thread first-touch.

**recommendation:** STAGE 0 first (biggest ROI, zero split hazard): add fault-around batching that keeps areas 4K. In mm/aspace/mod.rs handle_page_fault, on an anon write fault widen the populated range from one 4K page to a window (e.g. 16 pages, clamped to the area) in a single aspace-lock acquisition; CowBackend::populate already loops over pages, so only the range passed changes. This kills the per-fault fixed cost (trap + lock + area lookup) that dominates sysbench @1KB (42 MiB/s) and firsttouch, and is fully compatible with existing munmap/mprotect — no split needed. Expect firsttouch and @1KB to improve several-fold immediately. STAGE 1 (true THP-lite, 512x fewer faults + fewer TLB entries): opportunistically back large anon areas with 2MB blocks, reusing the already-complete stack (PageSize-parameterized backend + PT block support + contiguous alloc_frame). Gate on: anonymous && private && writable && thp_disable==0 && a fully-covered 2MB-aligned fault window && alloc_frame(Size2M) succeeds (else fall back to 4K). PREREQUISITE: implement split_huge (re-map the 2MB block as 512 identical 4K PTEs and downgrade the area/backend size to 4K) and call it from memory_set/src/set.rs unmap/protect (or in the Starry aspace before any sub-2MB op) so munmap/mprotect/mremap/madvise stay correct; also add graceful 4K fallback in alloc_frame and 4K fallback in CowBackend::populate. Do NOT round whole mmap areas up to 2MB. Concrete change sites: mm/aspace/mod.rs:587-622 (window/promote), mm/aspace/backend/cow.rs:233-296 & 508-560 (promote + split_to_4k + fallback), mm/aspace/backend/mod.rs:38-52 (alloc_frame fallback + optional DC-ZVA), syscall/mm/mmap.rs:179-201 & 531-544 (transparent size selection for large anon), optionally syscall/mm/brk.rs:65 and mm/loader.rs:725,745 (heap/stack). STAGE 2 (optional): DC-ZVA block-zero helper for the 2MB/4K zero path. Skip 1GB entirely (order-18 buddy allocation is unreliable). Verify with the harness rungs: firsttouch_s should fall toward Linux 0.086s and sysbench-memory @1KB-block should rise off 42 MiB/s.
