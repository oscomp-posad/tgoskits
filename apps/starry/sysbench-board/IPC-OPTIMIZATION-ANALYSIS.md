# IPC throughput bottleneck analysis (hackbench/schbench vs Linux)

Generated by the `ipc-throughput-bottleneck` workflow after the THP-EFAULT fix, when
hackbench/schbench first ran cleanly. Per-dimension traces of the pipe/futex
write→wake→read→block per-message cost, with ranked proposed changes.


## Syscall entry/exit + user-copy overhead (pipe write/read + futex wait/wake)

**Per-message cost:** One hackbench pipe message = write(100B)+read(100B) = 2 syscalls. Measured-from-code per message:

LOCKS (~11 acquire/release pairs):
- seccomp SpinNoIrq: 2 (one per syscall, syscall/mod.rs:52 -> task/mod.rs:369 = lock+clone)
- FD_TABLE RwLock read: 2 (get_file_like, file/mod.rs:281) + 2 Arc inc/dec
- aspace SLEEPABLE ax_sync::Mutex: ~5 — WRITE takes it TWICE (validate_user_read_buf then copy_user_read_buf, io.rs:141/143, each -> check_region -> access.rs:68 aspace.lock()), READ takes it 1-2× (VmBytesMut::write -> prepare_user_memory per ring slice, access.rs:358)
- pipe state Mutex: 2 (pipe.rs:209/248)
- PollSet wake internal: 2 (poll_rx/poll_tx.wake; alloc-free now)

ALLOCATIONS: 1 per message — sys_write's copy_user_read_buf does `.to_vec()` (io.rs:581) = a `Vec<u8>` bounce buffer from the GLOBAL-LOCKED TLSF allocator. (READ is alloc-free; block_on reuses cached AxWaker.)

PAYLOAD COPIES: 3 memcpy of 100B — WRITE: user->Vec (user_copy) + Vec->ring (memcpy); READ: ring->user (user_copy). Linux does 2 (user->pipe_page, pipe_page->user).

O(n) SCANS: 4-5 per message. Every check_region/prepare_user_memory calls can_access_range (axmm/aspace.rs:286, LINEAR `for area in self.areas.iter()`, n = process VMA count ~20-60) AND populate_area (mm/aspace/mod.rs:218, areas.find O(log n) + page-table cursor walk to eager-fault every covered page) — even for a 100B already-resident buffer.

ATOMICS: 2× set_accessing_user_memory set/clear per user_copy (access.rs:42/44), timer_state Kernel/User transitions, ptrace take_ptrace_syscall_trace_for per syscall (user.rs:74).

CONTEXT SWITCHES: write wakes reader (cross-core -> IPI + on_cpu handshake), read blocks -> 1 resched. (scheduler dimension.)

FUTEX per message: WAKE does validate_futex_word (sync/futex.rs:231 -> uaddr.vm_read -> aspace lock+populate for 4 bytes) + wq.wake allocates a Vec + O(waiters) retain (futex.rs:202) + a MANDATORY ax_task::yield_now() (sync/futex.rs:243) forcing a context switch on the waker. WAIT does uaddr.vm_read fast-path (aspace lock+populate 4B, futex.rs:203) + WaiterState Arc alloc + VecDeque push. Private-futex key resolution correctly SKIPS the aspace lock (futex.rs:471).

**vs Linux:** Linux's per-syscall fixed cost is tiny by comparison and that gap is the target here, not the pipe data movement. (1) Seccomp: Linux tests one TIF_SECCOMP thread-flag bit — no lock, no clone, usually skipped; Starry takes a SpinNoIrq and clones the whole SeccompState struct on every syscall (syscall/mod.rs:52). (2) User access: Linux copy_from_user/copy_to_user = access_ok() (a single bounds compare, USER_DS check) then the copy, with faults handled lazily by the #PF handler via the exception table — NO address-space lock, NO VMA walk, NO eager populate on the resident fast path. Starry takes the sleepable aspace Mutex, does an O(n_vma) linear can_access_range scan AND a populate_area page-table walk before EVERY copy (access.rs:68, 358) — and sys_write does the whole thing twice (validate + copy, io.rs:141/143). Starry already HAS the Linux-style machinery (user_copy.S returns bytes-remaining on fault via __ex_table, access.rs page_fault_handler does demand paging under access_user_memory), so the eager lock+walk+populate is redundant with the fault path for the common case. (3) Pipe write: Linux copies straight from user into the pipe buffer page; Starry allocates a global-TLSF-locked Vec bounce buffer and double-copies (io.rs:143). (4) Futex wake: Linux enqueues the woken task and returns (preempt only if higher prio); Starry forces ax_task::yield_now() on the waker every time (sync/futex.rs:243) and pays an aspace lock+populate to validate the 4-byte futex word (futex.rs:231). Net: Starry pays ~5 mutex acquisitions, 4-5 O(n) VMA scans/page-table walks, and 1 global allocation of fixed per-message overhead that Linux does not pay at all.

**Hotspots:**
- os/StarryOS/kernel/src/syscall/mod.rs:52-56 — seccomp_state().evaluate() runs on EVERY syscall entry
- os/StarryOS/kernel/src/task/mod.rs:368-370 — seccomp_state() = self.seccomp.lock().clone(): SpinNoIrq acquire + full SeccompState(mode+Vec) clone per syscall

- os/StarryOS/kernel/src/syscall/fs/io.rs:577-591 — copy_user_read_buf/validate_user_read_buf both call get_as_slice -> check_region
- os/StarryOS/kernel/src/mm/access.rs:48-79 — check_region: aspace.lock() (sleepable Mutex) + can_access_range + eager populate_area on every user access
- os/StarryOS/kernel/src/mm/access.rs:339-410 — prepare_user_memory (vm_read/vm_write path): same aspace-lock + populate before every user_copy
- os/arceos/modules/axmm/src/aspace.rs:279-306 — can_access_range: LINEAR scan of self.areas (n = VMA count) per copy

**Proposed changes:**
- **Seccomp fast-path: replace seccomp_state().evaluate() (SpinNoIrq lock + SeccompState clone every syscall) with an AtomicU8 mode flag checked lock-free at the top of handle_syscall; only lock+evaluate when mode != Disabled (filters installed is rare). Mirrors Linux's TIF_SECCOMP bit test.** (os/StarryOS/kernel/src/syscall/mod.rs:52-56, os/StarryOS/kernel/src/task/mod.rs:368-370, os/StarryOS/kernel/src/task/seccomp.rs) — win: Removes 2 SpinNoIrq acquire/release + 2 struct clones per message. ~5-10% of the fixed syscall-entry cost; scales with syscall rate (hackbench/schbench are syscall-bound).; risk: low
- **Lazy user-copy fast path (the big lever): stop eagerly locking the aspace + walking VMAs + populate_area on every copy. Do only check_access() bounds test (already exists, access.rs:316, no lock), run user_copy, and fall back to the aspace-lock + populate + retry ONLY when user_copy reports a fault (its return value + the existing __ex_table/#PF demand-paging path already handle this). This is exactly Linux's access_ok + extable model, and the machinery already exists in-tree.** (os/StarryOS/kernel/src/mm/access.rs:339-410 (prepare_user_memory/VmIo read+write), os/StarryOS/kernel/src/mm/access.rs:48-79 (check_region), os/arceos/modules/axmm/src/aspace.rs:279 (can_access_range)) — win: Removes ~4-5 sleepable-Mutex acquisitions + 4-5 O(n_vma) linear scans + page-table populate walks per message on the resident common case. Likely the single largest fixed-overhead reduction — order-of-magnitude on the copy-check portion; should move hackbench/schbench materially toward Linux.; risk: high
- **Kill the sys_write bounce buffer + double check_region: (a) call the user access-check once, not twice (drop the separate validate_user_read_buf when copy will re-check), and (b) copy straight from user memory into the pipe ring (a read-side VmBytes source, symmetric to sys_read's VmBytesMut) instead of allocating a Vec and double-copying.** (os/StarryOS/kernel/src/syscall/fs/io.rs:138-145,577-591, os/StarryOS/kernel/src/file/pipe.rs:230-280) — win: Removes 1 global-TLSF alloc/free pair (a cross-core contention point under many concurrent hackbench pairs) + 1 of 3 payload memcpys + 1 of 2 aspace checks per write. Moderate throughput win, larger at high concurrency.; risk: medium
- **Futex wake path: drop the unconditional ax_task::yield_now() after FUTEX_WAKE (let the scheduler preempt only when the woken task outranks the waker, like Linux), and replace validate_futex_word's full vm_read (aspace lock + populate) with the same lazy access-check as change #2.** (os/StarryOS/kernel/src/syscall/sync/futex.rs:229-245,49-55, os/StarryOS/kernel/src/task/futex.rs:217-229) — win: Removes one forced context switch and one aspace lock+populate per wake — directly targets schbench wakeup-latency/RPS, where per-wake cost dominates.; risk: medium


## Context-switch + reactor overhead per message (pipe & futex)

**Per-message cost:** MEASURED FROM CODE (steady-state hackbench: reader blocks on an empty pipe, writer does NOT block because the 64KiB ring is not full).

CONTEXT SWITCHES = 2 per delivered message, and this is NOT worse than Linux's minimum. The reader does one switch-OUT (block) and one switch-IN (wake); the writer stays running. What is worse is (a) the cost of each switch_to and (b) the futures-reactor scaffolding wrapped around each block/wake.

Per switch_to (components/axcpu/src/aarch64/context.rs:237-254), UNCONDITIONALLY every switch:
- 13 callee-saved GPR pairs saved+restored (context_switch asm, ~26 mem ops).
- FULL FP/NEON save+restore: fp_state.save()+restore() = 32 q-registers each way (~1KiB memory traffic) + fpcr/fpsr. fp-simd IS enabled (os/StarryOS/kernel/Cargo.toml:81-82), so this runs even for integer-only messaging tasks. Linux uses lazy/dirty FPU and skips it.
- TLS swap (tpidr_el0).
- IF the two tasks are different PROCESSES (different ttbr0): write_user_page_table + flush_tlb(None) = ENTIRE TLB FLUSH (context.rs:249-251). No ASID tagging (asm.rs:113 sets bare TTBR0_EL1). Thread-mode hackbench (shared aspace) skips this; process-mode pays a full TLB flush + refill storm every switch.
- on_enter/on_leave (os/StarryOS/kernel/src/task/mod.rs:500-518): a scope RwLock read + percpu ptr write + a force_read_decrement + perf_sched_in/out hooks — a handful of atomics per switch.

Locks taken on the pipe path per delivered message (~10 acquisitions): pipe state Mutex ×3 (poll_io runs the closure f() twice on the blocking poll + once on the post-wake success poll), PollSet SpinNoIrq ×2 (register + wake_drain), block_on woke SpinNoIrq ×3 (block side check/reset ×2 + wake side set ×1), target scheduler SpinRaw ×2 (sched_put_prev on wake + sched_pick on resched).
Atomics per message: transition_state CAS, on_cpu SeqCst load/store, occ_inc + occ_dec (fetch_add / fetch_update), nr_inc/nr_dec, preempt-pending, waker-clone refcount bump, and REMOTE_RESCHEDULE swap if cross-core. ~10-15.
Allocations on pipe path: 0 (cached AxWaker + alloc-free PollSet already landed).
IPIs: 0 if the wakee is placed on the waker's core; 1 for a cross-core wake; up to 2 in the deferred-wake race (put_task_with_state stashes and returns false while the wakee is still on_cpu → clear_prev_task_on_cpu re-enqueues + kick_remote_cpu again).
O(n) scans: PollSet::wake_drain scans len() entries, n = registered waiters on that pipe (≈1 for a pipe pair, capped 64). Ring as_slices is O(1).
REACTOR RE-POLLS: the closure f() (state-lock + ringbuf op) is invoked ~3× per delivered message — twice inside the blocking poll (optimistic call at poll.rs:27, then the lost-wakeup recheck at poll.rs:39 after register) and once on the post-wake success poll. A direct blocking wait would run the ringbuf body ~1×.

FUTEX message (FUTEX_WAIT that blocks + matching FUTEX_WAKE), MEASURED:
- 2 context switches (same switch_to cost as above).
- ALLOCATIONS, unlike the pipe path: 1 × Arc<WaiterState> per WAIT (futex.rs:109) + 1 × Vec per WAKE (futex.rs:218), plus VecDeque growth and FutexTable HashMap entry alloc/free churn (get_or_insert at insert, FutexGuard::drop at empty). These hit the global TLSF allocator lock → serialize all CPUs under many-thread schbench.
- O(n) wake: queue.retain scans every waiter in the bucket (futex.rs:200-213); a spurious re-poll does an O(n) iter_mut().find (futex.rs:128).
- Locks: bucket Mutex (a SLEEPABLE ax_sync::Mutex, heavier than a spinlock) on both wait-push and wake-retain; FutexTable HashMap Mutex ×2.

**vs Linux:** Linux's 2 switches/message are each far cheaper AND carry less scaffolding. (1) Lazy FPU: Linux's fpsimd_thread_switch skips NEON save/restore for integer-only tasks via a per-task dirty flag; StarryOS saves+restores all 32 q-regs every switch. (2) ASID/PCID-tagged TLBs: Linux writes TTBR0 with an ASID and does NOT flush on a process switch; StarryOS flushes the entire TLB on every cross-aspace switch, so process-mode messaging eats a full TLB refill storm each hop. (3) Integrated wait: Linux pipe_read/pipe_write take pipe->mutex once and use an in-place wait_queue entry — no separate poll object, no double re-run of the copy path, no per-op allocation. StarryOS runs the ringbuf closure ~3×/message through poll_io, appends+drains a PollSet, and does a woke-flag interlock. (4) Futex: Linux queues an on-stack plist node under a per-bucket hashed lock with no kmalloc per wait and a targeted wake; StarryOS allocates an Arc<WaiterState> per wait + a Vec per wake and does an O(n) bucket retain, all serialized on the global TLSF lock. These per-switch and per-block constant factors, compounded by the global-allocator serialization on the futex path, are what turn a same-count 2-switch protocol into the measured 10–260× gap; they are not extra context switches but heavier ones wrapped in a heavier reactor.

**Proposed changes:**
- **Lazy/dirty FP-SIMD save-restore: trap EL0 FP via CPACR and save+restore the 32 NEON regs only for tasks that actually used FP this slice (mirror Linux fpsimd_thread_switch / TIF_FOREIGN_FPSTATE). Removes ~1KiB of unconditional register traffic from every one of the 2 switches/message for integer-only hackbench/schbench tasks.** (components/axcpu/src/aarch64/context.rs:243-247 (+ a per-task fp-dirty flag in axtask task.rs and a CPACR trap handler)) — win: ~5-15% on switch-bound messaging (removes a large fixed per-switch cost that Linux does not pay); scales with switch rate; risk: medium
- **ASID-tagged TTBR0 so a cross-process switch does a bare TTBR0 write with no flush_tlb(None). Allocate/recycle ASIDs per aspace, set the ASID field in TTBR0, drop the full-TLB flush in switch_to. Only affects process-mode (different-aspace) switches.** (components/axcpu/src/aarch64/context.rs:249-251, components/axcpu/src/aarch64/asm.rs:113 (write_user_page_table), aspace/page-table root plumbing) — win: order-of-magnitude for multi-process messaging (kills a full TLB-refill storm per switch); ~0 for thread-mode (shared aspace already skips); risk: high
- **Collapse the reactor double-poll on the blocking path: after register(), recheck readiness with the cheap pollable.poll() event mask instead of re-running the full I/O closure f(); run the heavy ringbuf/state-lock body only when it will actually make progress. Cuts the pipe state Mutex acquisitions + ringbuf passes from ~3 to ~2 per delivered message.** (os/arceos/modules/axtask/src/future/poll.rs:26-51, os/StarryOS/kernel/src/file/pipe.rs:207-227) — win: ~5-10% on the pipe path; larger under cross-CPU contention on the shared pipe state Mutex; risk: medium
- **Make the futex wait/wake path allocation-free: put the WaiterState in an intrusive on-stack node linked into the bucket (like the cached-AxWaker pattern) instead of Arc::new per wait, and wake into a fixed stack array instead of a fresh Vec. Removes the two per-op global-allocator hits that serialize CPUs under many-thread schbench.** (os/StarryOS/kernel/src/task/futex.rs:109 and :217-228) — win: large under many-core schbench (removes global TLSF-lock serialization from every FUTEX_WAIT/WAKE); modest single-thread; risk: medium
- **Add an adaptive spin-then-block before future_blocked_resched: on Pending, spin-recheck the future a bounded number of iterations (or until a sibling is seen running on another core) before switching out, so a wake that lands within the spin window avoids the block+wake switch pair entirely (Linux adaptive-mutex / MWAIT analog).** (os/arceos/modules/axtask/src/future/mod.rs:100-124) — win: can drop from 2 switches to 0 on tightly-coupled ping-pong messages when the peer wakes within the spin window; workload-dependent, board A/B needed; risk: medium
- **Reduce cross-core wake IPIs: enable a narrowed wake_affine that co-locates only true 1:1 sync pairs on the waker's core (keeping the fan-out spread that regressed the broad version), turning cross-core wakes into local enqueues and avoiding the up-to-2-IPI deferred-wake handshake.** (os/arceos/modules/axtask/src/run_queue.rs:596-684 and the deferred path :1367-1405) — win: removes 1 IPI + a cache-cold refill per message for pipe/lock hand-off pairs; neutral-to-negative for fan-out (hence the pair-only gate); risk: high


## O(n) scans + lock contention under load — every hot-path operation whose cost scales with task/waiter count (n = waiters on one futex key; N = threads sharing a process). Verdict split by workload: the PIPE path (hackbench) has NO O(n)-in-taskcount scan and NO shared lock, so this dimension does not bite it; the entire super-linear blowup lives in the FUTEX path (schbench / glibc mutex+condvar). Board build uses the per-CPU buddy-slab allocator (os/StarryOS/kernel/Cargo.toml:72 comment), so the global-allocator lock is NOT the contention point — the single per-process futex-table Mutex is.

**Per-message cost:** PIPE MESSAGE (one write→read roundtrip), verified against pipe.rs write()/read() + axpoll wake_drain + run_queue wake: O(n)-in-taskcount scans = ZERO. Each pipe has exactly 1 reader + 1 writer, so the PollSet it wakes has n=1 registered waker (components/axpoll/src/lib.rs:203 loop runs once, capped 64 regardless). Locks/message: pipe-state Mutex ×2 (one per side), poll_rx/poll_tx SpinNoIrq ×1 per wake, target-CPU scheduler SpinRaw ×1 per wake — all per-pipe or per-CPU, never contended by the other 399 tasks. Cross-core wake adds 1 IPI (run_queue.rs kick_remote_cpu) + 2 context switches. No global lock, no allocation (cached AxWaker + alloc-free PollSet already landed). CONCLUSION: in this dimension pipes are already clean; their 10x gap is fixed per-switch cost (a different dimension), not scans.

FUTEX WAKE(1) on a key with n live waiters (schbench / cond_signal / contended mutex unlock), verified against syscall/sync/futex.rs:229-245 + futex.rs:200-229,590-607: per-process futex-table Mutex acquired 2× (FutexTable::get at futex.rs:531, then FutexGuard::Drop at futex.rs:597); TWO O(n) VecDeque scans — wake_locked queue.retain (futex.rs:202, under the WaitQueue lock) AND is_empty queue.retain (futex.rs:405-408, run INSIDE FutexGuard::Drop at futex.rs:603 while HOLDING the single table lock); 1 wakers Vec alloc (per-CPU slab, cheap); 1 forced ax_task::yield_now() (syscall/sync/futex.rs:243) = an extra reschedule + scheduler-lock acq per wake; plus the woken task's unblock (1 scheduler-lock + maybe 1 IPI). Net: the table lock every one of N threads needs is held for O(n) time each op → aggregate O(N·n) ≈ O(N²) serialized wall time. FUTEX WAIT (futex.rs:181-198 + syscall futex.rs:201-227): table Mutex ×2 (get_or_insert + guard drop w/ O(n) is_empty), push_back O(1), and each spurious re-poll does a linear iter().find (futex.rs:128-134) O(n). FUTEX_CMP_REQUEUE (glibc cond_broadcast, syscall futex.rs:246-289 → wake_requeue_locked futex.rs:287-299): src.retain O(n) + wake loop of VecDeque::remove(index) which is O(n) each → O(n·wake_count); requeue drain is pop_front/push_back O(n). n ranges up to N-1 (~hundreds at hackbench g=10 / 400 tasks); frequency = every contended lock/unlock/wait/signal (millions/run). NOTE: SHARED_FUTEX_TABLES O(m log m) retain (futex.rs:626) is OFF this path — hackbench/schbench use FUTEX_PRIVATE_FLAG → FutexKey::Private → proc_data.futex_table (futex.rs:646), never the shared BTreeMap.

**vs Linux:** Linux futex uses a GLOBAL hash table of ~256×ncpu buckets keyed by hash(mm,addr), each with its own spinlock (futex_hash_bucket->lock). Different futex words land in different buckets → wakes/waits on distinct locks run fully in parallel across cores, and each bucket's plist holds only that bucket's waiters so a wake walks O(waiters_in_bucket) ≈ O(n/buckets), not O(all-process-waiters). StarryOS collapses all of a process's private futexes onto ONE Mutex<HashMap> (futex.rs:514): zero sharding, so N threads serialize on one lock. Worse, StarryOS runs an O(n) VecDeque scan (is_empty retain) INSIDE that lock on every op (futex.rs:603) — Linux never holds a lock across an O(n) rescan; its hb->lock is held only for the plist splice/walk of the tasks actually being touched. And Linux FUTEX_WAKE(k) walks only until k are woken (ordered plist), whereas wake_locked always retains across all n. Net: Linux is O(n/buckets) with per-bucket parallelism; StarryOS is O(n) serialized on one lock → the measured schbench tail blows up as ~O(N²) where Linux stays flat. (PIPE path is comparable to Linux in this dimension — both are per-object, no shared scan.)

**Proposed changes:**
- **Shard the per-process futex table: replace FutexTable's single Mutex<HashMap> with a fixed array of B buckets (e.g. 64), each an independent Mutex<HashMap>, selected by a hash of key.as_usize(). ## Allocations per message (pipe read+write+wake path and futex wait/wake path, post cached-waker + alloc-free PollSet)

**Per-message cost:** PIPE (1 message = 1 write + 1 read, steady state): 1 heap alloc + 1 free — the writer-side Vec<u8>(msg_len) bounce buffer in sys_write (copy_user_read_buf -> to_vec). The read side is fully zero-copy (VmBytesMut writes straight to user memory) and block_on/PollSet::wake are alloc-free, so the read/wake half is 0 alloc. That single alloc+free = 2 allocator-lock acquisitions (per-CPU buddy-slab SpinNoIrq on the board; the ONE global SpinNoIrq under a TLSF build). Other per-msg costs on this path (measured from code, not allocations): pipe-state Mutex x2, FD_TABLE RwLock-read x2, scheduler SpinRaw x>=2, PollSet SpinNoIrq x2, Arc inc/dec on the file + waker, one occ_inc/occ_dec pair, one transition_state CAS, ~2 context switches (reader blocks then resumes), 0-1 cross-core IPI (occ wake prefers idle-prev/least-loaded; a hackbench cross-core wake costs 1 kick_remote_cpu). No O(n) scans on the pipe path (PollSet drain is bounded <=64).

FUTEX (1 message = 1 WAIT + 1 WAKE): 2 allocs + 2 frees. WAIT side = 1 Arc<WaiterState> (futex.rs:109); WAKE side = 1 wakers Vec (futex.rs:218/225). (+1 BTreeMap node if the wait carries a timeout; +1 amortized Arc<FutexEntry> the first time a given address is used.) = 4 allocator-lock acquisitions/msg. WAKE also does an O(n) queue.retain scan (n = waiters parked on that futex word) and the WAIT re-poll does an O(n) iter().find on a spurious wake. Plus WaitQueue inner Mutex, FutexTable Mutex (get_or_insert / get / guard-drop) + HashMap probe, and a yield_now() after wake (extra context switch).

Bottom line: pipe = 1 alloc+free/msg, futex = 2 alloc+free/msg. All are small (~100 B for hackbench, ~40 B Arc/Vec) but every one takes an IRQ-off allocator spinlock, and on a TLSF build they all serialize on a single global lock -> the super-linear collapse under many senders.

**vs Linux:** Linux is 0-alloc on BOTH paths; StarryOS is 1 (pipe) / 2 (futex) alloc+free per message. (1) Linux pipe_write copies user bytes straight into a pooled, recycled pipe_buffer page (the pipe->bufs ring, up to 16 pages) with copy_page_from_iter under the pipe mutex — no per-write slab allocation. StarryOS instead kmalloc-equivalents a fresh Vec<u8> in sys_write, copies user->Vec, then copies Vec->ringbuf a second time inside the pipe lock: a redundant intermediate that the pre-existing HeapRb vacant slices make unnecessary. (2) Linux futex_wait parks an on-stack futex_q linked into the hash-bucket plist (no kmalloc), and futex_wake collects victims through an on-stack wake_q list threaded via task_struct->wake_q.next (no kmalloc, no Vec). StarryOS heap-allocates an Arc<WaiterState> per wait and a wakers Vec per wake. Because each StarryOS alloc/free grabs an IRQ-off allocator spinlock, and under the TLSF backend that is ONE global lock, N concurrent senders serialize on the allocator that Linux never touches — this is the mechanism behind the 10-260x messaging gap once the futex/fork EFAULT is fixed. On the board's buddy-slab backend the lock is per-CPU (same-CPU alloc+free, so no cross-CPU serialization), which softens but does not remove the cost: still 2 (pipe) / 4 (futex) IRQ-off spinlock + freelist ops per message that Linux spends 0 on.

# RANKED PLAN — Close the StarryOS IPC-per-message gap

**The gap splits cleanly by workload, and the two halves have different bottlenecks — do not conflate them:**
- **hackbench (pipe)** = *fixed per-message constant factor*. No shared lock, no O(n)-in-taskcount scan (each pipe has 1 reader/1 writer). Its 10× is heavy syscall-entry + user-copy + switch scaffolding.
- **schbench (futex)** = *super-linear O(N²) collapse*. One per-process futex-table `Mutex` held across an O(n) scan → the only genuinely super-linear term in the system. This is what produces the 260× tail.

Ranking is win/risk descending. Tier 1 = do now (board-independent, provable in QEMU-smp).

---

## THE SINGLE BIGGEST LEVER

**Futex table: O(1) emptiness + shard the lock (schbench 260× → toward flat).** This is the headline because it is the *only* change that removes a super-linear term. Everything else is a constant factor. Two coordinated edits:

### L1 — Make WaitQueue emptiness O(1); never hold the table lock across an O(n) scan
- **What:** Add an `AtomicUsize` live-waiter count to `WaitQueueInner` (inc on `push_back`, dec on wake/cancel/remove). Replace the `queue.retain`-as-emptiness-test in `is_empty()` and in `FutexGuard::Drop` with the counter. Make `wake(count)` pop live waiters FIFO until `count`/bitset satisfied instead of `retain` over all n.
- **Where:** `os/StarryOS/kernel/src/task/futex.rs:200-213` (`wake_locked`), `:403-409` (`is_empty`), `:603` (`FutexGuard::Drop` — the O(n)-under-the-lock that *is* the O(N²) mechanism), `:127-135` (kill the linear `iter().find` on re-poll by storing the `Waker` in `WaiterState`).
- **Win:** Order-of-magnitude on schbench tail. Turns per-op lock-hold from O(n) → O(1). **Largest single contributor even before sharding.**
- **Risk:** medium (counter/queue must stay in sync across cancel/timeout/requeue).
- **Board-independent:** YES — algorithmic; visible in QEMU-smp4 as flat vs. quadratic hold time.

### L2 — Shard the per-process futex table into B buckets (e.g. 64), each own `Mutex<HashMap>`
- **What:** Replace `FutexTable(Mutex<HashMap>)` with `[Mutex<HashMap>; 64]` selected by `hash(key.as_usize())`. Mirrors Linux `futex_hash_bucket`.
- **Where:** `os/StarryOS/kernel/src/task/futex.rs:514` and `get`/`get_or_insert`/`remove_waiter`/`FutexGuard::Drop`.
- **Win:** Lifts aggregate contended-futex throughput from ~1 core toward ~ncpu (up to ~8× on RK3588). Removes the single-lock serialization tail.
- **Risk:** medium.
- **Board-independent:** YES — algorithmic; QEMU-smp shows parallel bucket progress.

> L1 before L2: O(1)-emptiness is worthless-to-negative if you still serialize on one lock, and it's the bigger term. Land L1, then L2.

---

## TIER 1 — do next (board-independent, high win/low-med risk)

### L3 — Kill the `sys_write` bounce `Vec` + double check_region (highest-leverage *pipe* change)
- **What:** (a) Drop the separate `validate_user_read_buf` — the copy re-checks anyway, so this halves the aspace checks on write. (b) Copy straight from user memory into the pipe ring: pass a zero-copy `VmBytes` source (mirror of `sys_read`'s already-zero-copy `VmBytesMut`) into `file_like.write(...)`, so the ringbuf's existing `vacant_slices_mut()` copy reads user memory directly — no intermediate `Vec`, no double memcpy.
- **Where:** `os/StarryOS/kernel/src/syscall/fs/io.rs:141,143,577-591`; `os/StarryOS/kernel/src/file/pipe.rs:241-279` (write closure); add `VmBytes` reader in `mm/access.rs`.
- **Win:** Removes the dominant pipe alloc (1 alloc+free/write) + one of two aspace checks + one of three memcpys. On a TLSF build this deletes the global-lock acquire/release pair that drives the super-linear term under many senders; on buddy-slab it removes 2 per-CPU spinlock ops/write. hackbench is write-dominated → highest-leverage single pipe change.
- **Fallback if reading user memory under the pipe `Mutex` is fault-risky** (the original reason for the bounce): keep the copy but source from a **per-task reusable scratch buffer** (same lifecycle trick as the already-landed cached `AxWaker`) — alloc once per thread, not per write.
- **Risk:** medium.
- **Board-independent:** YES (alloc/lock/copy count reduction; contention win scales on board).

### L4 — Seccomp fast-path: lock-free `AtomicU8` mode check
- **What:** Replace `seccomp_state().evaluate()` (`SpinNoIrq` lock + full `SeccompState` clone *every syscall*) with an `AtomicU8` mode flag tested at the top of `handle_syscall`; only lock+clone+evaluate when `mode != Disabled` (filters installed is rare). Mirrors Linux's `TIF_SECCOMP` bit.
- **Where:** `os/StarryOS/kernel/src/syscall/mod.rs:52`; `os/StarryOS/kernel/src/task/mod.rs:368`; `task/seccomp.rs`.
- **Win:** Removes 2 spinlock acquire/release + 2 struct clones per pipe message (per syscall). ~5-10% of fixed syscall-entry cost; scales with syscall rate. hackbench/schbench are syscall-bound.
- **Risk:** LOW. **Best win/risk ratio in the whole plan after L1.**
- **Board-independent:** YES.

### L5 — Lazy user-copy fast path (the big *hackbench* lever)
- **What:** Stop eagerly `aspace.lock()` + linear `can_access_range` VMA scan + `populate_area` page-table walk on *every* copy. Do only the bounds test (`check_access`, no lock), run `user_copy`, and fall back to lock+populate+retry **only when `user_copy` reports a fault** — the `__ex_table` / `#PF` demand-paging path already exists in-tree and already handles this. This is exactly Linux's `access_ok` + extable model.
- **Where:** `os/StarryOS/kernel/src/mm/access.rs:48-79` (`check_region`), `:339-410` (`prepare_user_memory`); `os/arceos/modules/axmm/src/aspace.rs:279` (`can_access_range`).
- **Win:** Removes ~4-5 sleepable-`Mutex` acquisitions + 4-5 O(n_vma) linear scans + populate walks per pipe message on the resident common case. **Single largest fixed-overhead reduction for hackbench** — order-of-magnitude on the copy-check portion.
- **Risk:** HIGH — changes the fault model on the hot path. Must prove the fault → populate → retry loop is correct under the pipe `Mutex` and futex-word read, and that `set_accessing_user_memory` + the `#PF` handler cover every entry. Land behind a feature gate; validate the fault path in QEMU with a deliberately-unmapped buffer test before trusting the fast path.
- **Board-independent:** YES (lock/scan count); the win magnitude is algorithmic, shows in QEMU.

> Ranked below L3/L4 despite bigger raw win because of the HIGH correctness risk. It is the biggest hackbench lever once L3/L4 de-risk the path.

## TIER 2 — high win but HARDWARE-TIMING-dependent (board A/B required; QEMU-TCG hides the win)

### L6 — Lazy/dirty FP-SIMD save-restore
- **What:** Trap EL0 FP via CPACR; save/restore the 32 NEON q-regs only for tasks that touched FP this slice (mirror `fpsimd_thread_switch`/`TIF_FOREIGN_FPSTATE`). Integer-only hackbench/schbench tasks stop paying ~1 KiB of register traffic on *every* one of the 2 switches/message.
- **Where:** `components/axcpu/src/aarch64/context.rs:243-247` + per-task fp-dirty flag + CPACR trap handler.
- **Win:** ~5-15% on switch-bound messaging; scales with switch rate.
- **Risk:** medium (broad — affects *every* context switch system-wide; wrong dirty-tracking = FP-state corruption).
- **Hardware-timing:** the memory-traffic saving is largely invisible in QEMU-TCG; real win is board-only. Instruction-count reduction is provable in QEMU.

### L7 — ASID-tagged TTBR0 (process-mode only)
- **What:** Allocate/recycle ASIDs per aspace, set the ASID field in TTBR0, drop `flush_tlb(None)` from cross-aspace `switch_to`.
- **Where:** `components/axcpu/src/aarch64/context.rs:249-251`, `asm.rs:113`.
- **Win:** order-of-magnitude for **multi-process** messaging (kills a full TLB-refill storm per switch). **~0 for thread-mode hackbench** (shared aspace already skips the flush).
- **Risk:** HIGH (TLB correctness / ASID rollover).
- **Hardware-timing:** YES — QEMU-TCG does not model TLB refill cost; board-only win. Only pursue if the target workload runs process-mode.

### L8 — Adaptive spin-then-block before `future_blocked_resched`
- **What:** On `Pending`, bounded spin-recheck before switching out, so a wake landing in the window skips the block+wake switch pair.
- **Where:** `os/arceos/modules/axtask/src/future/mod.rs:100-124`.
- **Win:** 2 switches → 0 on tightly-coupled ping-pong; workload-dependent.
- **Risk:** medium; **can waste cycles / hurt fairness under contention** — needs board A/B.
- **Hardware-timing:** YES.

## TIER 3 — secondary / cheap / insurance

- **L9 — Collapse the reactor double-poll** (`future/poll.rs:26-51`): after `register()`, recheck via the cheap `poll()` event mask instead of re-running the full ringbuf closure `f()`; run the heavy body only when it will progress. - **L12 — Keep buddy-slab per-CPU allocator on every messaging build** (`axalloc` tlsf vs buddy_slab): insurance so any *residual* alloc hits a per-CPU lock, not the global `SpinNoIrq`. Little benefit once L3/L10/L11 remove the allocations. LOW risk.

## REGRESSION WATCH — do NOT ship these as written

1. **wake_affine / cross-core-wake co-location narrowing** (dim-3 proposal, `run_queue.rs:596-684`, `:1367-1405`). **This directly touches the placement work and would regress it.** The occ-aware placement already ships; `wake_affine` + runtime migration are deliberately opt-in/off because the broad version **regressed sysbench threads=1 by 0.46× (migration thrash)**. Re-enabling any co-location/migration lever risks both the validated **sysbench t=8=4686** and the merged big.LITTLE placement subset. **Excluded from this plan.** If ever revisited, gate to true 1:1 sync pairs only, off by default, board-A/B against 4686 before merge.

2. **Unconditional removal of `yield_now()` after `FUTEX_WAKE`** (`sync/futex.rs:243`). Tempting (one forced switch + sched-lock per wake), but removing it naively can *regress* schbench wakeup latency if the woken higher-prio waiter no longer preempts the waker. **Gate, don't delete:** yield only when the woken task outranks the current one (Linux semantics). Marked high-risk for good reason.

3. **L6/L7 (FP-SIMD, ASID)** are system-wide axcpu changes. They should not algorithmically affect sysbench t=8 (steady-state memory workload is switch-light), but a correctness bug there corrupts *everything*. Feature-gate and validate the FP/TLB path before wiring into the default build.
