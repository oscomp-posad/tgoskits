# 与类似项目的对比分析

> 对应技术方案 §3.1.2「与类似项目的对比分析」。对比分三层展开，第一层与同机同模型的 Linux 基线，第二层与外部同类工作，第三层与工业标杆。外部条目均给出可核查来源，无公开数字处一律标注「未公开」。

## 一、与 Linux 基线（同一机器人、同一可执行文件、不同操作系统）

这是本工作最可控的一层对比。同一台 RK3588（OrangePi 5 Plus）、同一份应用可执行文件、同一个 RKNN 模型、同一颗片上 NPU，仅把底层操作系统从基于 C 的 Linux 换成以 Rust 实现的 Starry（构建于 ArceOS 组件）。

- 推理时延口径一致，可直接比较。在 480×640、整数输出路径（`want_float=0`，按需反量化）、推理亲和性固定到 A76 大核下，Starry 端到端 p50 由最初 30.6 ms 优化到 11.75 ms，与同机 Linux 的 11.4 ms 持平，不超越。`run_ms` 与 RKNN 运行时自报的 `run` 时间相符，说明 NPU 的一次前向是真实计算而非空转等待。
- 拉平差距的关键动作是整数路径取回输出。`outputs_get` 的 INT8 到 FP32 反量化原本是约 12 ms 的首位开销，改为整数域阈值先筛背景、只对存活单元做反量化后消除，且在 285 张测试图上与浮点路径逐一一致。
- 前处理改走 RGA。letterbox 由 CPU 缩放路径降到 RGA 硬件路径，复现了硬件零拷贝前处理，而非自定义路径。
- 诚实边界。本工作只主张推理时延与 Linux 持平。启动时间、内存占用与能耗等结构性优势实测待补，本文标注未公开，不作超越声明。

## 二、与外部同类工作

从公开、可核查的工作中选取三个最相关的对照。

### Ariel-ML（基于 Ariel OS，前 RIOT-rs）

这是这批 Rust 操作系统中少数在真实硬件上做神经网络推理的工作，因而最贴近本工作的「非 Linux 真机推理」定位。两者的差异落在两个正交维度。Ariel-ML 在微控制器级硬件上以多核 CPU 并行（贪心调度跨核分派算子，无专用加速器），模型小，延迟约 20 ms 到 1.6 s（双核 RP2040 相对单核最多约 1.6 倍加速）；本工作在 SoC 级的 RK3588 上接入片上 NPU 跑 YOLOv8/RKNN，480×640 端到端 11.75 ms，并跑通完整机器人回路。该工作的论文（2025-12）明确指出 Tock、Embassy、Ariel 等 Rust 嵌入式操作系统目前都不提供通用机器学习框架支持，可用于说明「非 Linux 真机推理」在生态中的稀缺。
来源：https://arxiv.org/html/2512.09800 ，https://github.com/ariel-os/ariel-ml 。

### mtx512/rk3588-npu（逆向工程）

在方法学上与本工作的 rknpu 设备层最相关，思路同族，都绕开闭源的 librknnrt.so，直接按技术手册与任务队列向 NPU 提交命令。差异在于，该工作仍在 Linux（C）下，以矩阵乘与 llama2.c 验证正确性，未做完整的 YOLOv8 视觉回路，也未给出系统化的延迟数字；本工作把同类直驱思路落到 Rust 的 Starry/ArceOS（含 OSAL 抽象、任务提交、中断与内存管理），跑通 YOLOv8 端到端与真板机器人回路并给出 11.75 ms。可引为「裸寄存器与作业直驱路线可行」的旁证与起点。
来源：https://github.com/mtx512/rk3588-npu ，http://jas-hacks.blogspot.com/2024/02/rk3588-reverse-engineering-rknn.html 。

### OSComp 2024 proj311《基于飞腾派部署 ArceOS 实现智能小车驱动》（一等奖）

操作系统大赛中与本工作最可比的真机硬件闭环同行，同属 ArceOS 生态、同为国产 ARMv8 真板，同样从零实现 USB 主机栈、I2C 电机驱动与真机机器人联动。差异在于，该项目停在 HID 到电机控制，未打通相机到 NPU 的推理，报告也未给出性能数字；本工作在其基础上多走了 RGA、JPU、rknpu 与 YOLOv8/RKNN 端到端推理，以及硬件 PMU perf，并有与 Linux 可核查的 11.75 与 11.4 ms。两者的客观差异落在加速器接入与端到端可核查数字上，本工作仍只主张推理与 Linux 持平。
来源（提交页，登录可见）：https://gitlab.eduxiji.net/educg-group-26009-2210132/T202412799992620-3566 ；GitHub 镜像：https://github.com/Jasonhonghh/arceos_experiment 。

其余 Rust 操作系统不列入推理时延对比。Tock、Hubris、Theseus、Drone、Bern 等均无 NPU 接入与推理负载，其价值维度是 Rust 类型安全与内存保护带来的可靠性与隔离，与本工作不在同一坐标上。Hermit（RustyHermit）配合 Cricket 虽属「Rust 操作系统加硬件加速器」，但它是云与 HPC 场景的 unikernel，经远程过程调用转发 NVIDIA GPU（间接、x86_64），与本工作的边缘 aarch64 本地直驱片上 NPU 加零拷贝在接入方式上根本不同。

## 三、与工业标杆（Linux 加 RKNN 生产路径）

工业事实标准是 Rockchip 官方的 RKNPU2 Runtime（librknnrt）配合 RKNN-Toolkit2。在 PC 端把 ONNX 编译并量化为 RKNN，在板端用闭源的 librknnrt.so 于三核 NPU 上推理，本工作所用的 YOLOv8/RKNN 模型即来自这条标准路径。本工作没有使用这个闭源运行时，而是在 Starry/ArceOS 内自实现 rknpu 设备层，并自写 RGA 与 JPU 驱动且对齐真实的用户态接口（RGA 对齐 librga，JPEG 对齐 Rockchip MPP 的 `mpp_service`），而非自定义接口。

工业基线的公开延迟口径为仅模型推理、不含前后处理、最大 NPU 频率、单核。官方 `rknn_model_zoo` 给出 RK3588、640×640、INT8 下 YOLOv8n 约 73.5 FPS（约 13.6 ms 纯推理），YOLOv5n 82.5、YOLOv11n 60.0 FPS。需注意口径不同，这些是纯推理，本工作的 11.75 ms 是 480×640 含端到端回路，二者不可直接相减或并列。本工作的目标不是刷新 NPU 纯推理纪录，而是证明 Rust 的 Starry 内核栈能在同硬件上复现工业级的 NPU、RGA、JPU 路径并端到端打通。
来源：https://github.com/airockchip/rknn-toolkit2 ，https://github.com/airockchip/rknn_model_zoo ，https://github.com/airockchip/librga ，https://github.com/rockchip-linux/mpp 。

## 五、口径与诚实说明

- 可直接比较的只有一组，即本工作与同机 Linux 基线的 11.75 与 11.4 ms。两者同一台 RK3588、同一份可执行文件、同一个 RKNN 模型、同一颗 NPU、同为 480×640 含端到端回路口径，结论是持平，不超越。
- 不可直接比较的是工业标杆数字。`rknn_model_zoo` 与社区复测均为纯模型推理、不含前后处理、最大 NPU 频率、单核，分辨率多为 640×640，与本工作的 480×640 含回路口径不同，不能相减或并列排名，比较帧率时还须注明单核与三核之别。
- 硬件与模型量级不同的项目不比较延迟。Ariel-ML 是微控制器加小模型加多核 CPU，mtx512 与 proj311 无 YOLOv8 端到端延迟数字。这些项目与本工作的客观差异落在是否接专用 NPU、目标硬件量级、是否真机机器人闭环、以及接入方式（本地直驱、远程过程调用、多核 CPU）之上，而非单纯比延迟。
- 本工作不主张超越 Linux 推理，仅主张推理时延与 Linux 持平。其差异化价值在于非 Linux 的自研 Rust 内核加真板端到端，以及配套的 RGA、JPU、perf 与块设备容错驱动并部分合并上游，而非刷新 NPU 纯推理纪录。
