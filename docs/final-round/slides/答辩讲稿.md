**【开场】** *(约 1:00)*

各位老师好，我们是清华大学 Posad 队。

我们的工作从一台会捡网球的机器人说起。它原本运行在 C 语言的 Linux 上，我们把整台机器的操作系统换成了用 Rust 写的 StarryOS，硬件平台是 RK3588 这类边缘芯片。初赛阶段，我们让机器人在 StarryOS 上重新跑起来，并把视觉推理的延迟追平了 Linux。进入决赛，我们把目标定得更高——让 StarryOS 作为一个通用操作系统，在调度、内存、频率、启动这些与机器人无关的子系统上，也逐项与 Linux 对比，能追平的就追平，能超越的就超越。整个过程中，两侧始终运行同一份 ELF 二进制，任何差异都只来自内核本身。

要逐项对比，先得看清慢在哪里。为此，我们从零给 StarryOS 实现了一套基于硬件 PMU 的 perf，覆盖单核与大小核、缓存事件、调用栈，以及 kprobe 到 ftrace 的追踪能力。这套 perf 我们也在真机上完整验证过，各项都能稳定工作。有了它，我们才能把性能瓶颈定位到具体的内核层和函数上。

**【视觉链路：三块加速器驱动 + 零拷贝】** *(约 1:20)*

先看机器人这条链路。一帧图像进来，需要经过解码、缩放、色彩转换，送入 NPU 推理，再取回结果。这三步若放在 CPU 上，每一步的代价都和一次推理相当；如果全部由通用核承担，感知任务就会与运动控制争抢核心资源。所以我们把这三步分别交给 RK3588 上的三块专用硬件，而这三块硬件的驱动都是我们自己写的：JPU 负责硬件 JPEG 解码，RGA 负责缩放和色彩转换，NPU 这边我们修好了连续推理所需的缓冲管理。再往上是内存路径的优化，我们通过 dma-buf 让三块加速器共享同一段物理内存，一帧数据从相机进入，经 JPU、RGA 再到 NPU，全程零拷贝。最终的结果是：硬件解码一帧只需 1 毫秒，输出与 Linux 逐字节一致；色彩转换比 CPU 实现快 7 倍。

硬件链路之外，软件上我们又做了三件事：把推理任务绑定到 A76 大核；改用整数方式取回结果，只反量化那几十个实际用到的单元；按相机原生分辨率重新导出模型，同时换掉一个偏慢的激活函数。这三项叠加之后，捡球用的小模型端到端推理延迟是 11.75 毫秒，与 Linux 的 11.4 毫秒基本持平；更重的 640 模型，从落后 6.3 倍收窄到 2.1 倍。剩下的差距，主要在单核用户态的那几步。

**【系统层：逐项和 Linux 较量】** *(约 1:40)*

系统层的对比，我选几个有代表性的点来说。

getpid 这类几乎不做实际工作的空调用，最能反映进出内核的固定开销。我们一开始测出来是 1200 纳秒，相当于 Linux 的七倍。慢在返回路径上三处每次都会执行、但大多数场景根本用不到的记账操作。我们把这三处都改成按需执行，getpid 降到 431 纳秒，与 Linux 的差距收窄到 2.6 倍。

内存方面，我们确实比 Linux 快。128 兆内存首次访问并建立页表，我们花 30 毫秒，Linux 是 86 毫秒，快了接近三倍。做法是用大页一次建好，同时省掉了一次新建映射时本不需要的 TLB 刷新。

频率管理这块，背后是一个硬件上的发现。RK3588 的 CPU 频率和电压是绑定的，不能像普通时钟那样直接设定频率，Linux 的做法是为每个档位精确配置电压。我们找到的路径是 PVTPLL 的环长——同样的电压下，环拉得越长，频率就越高。靠这个机制，每个核在同频下就能与 Linux 打平。

启动时间我们也实现了反超：从上电到输出第一帧推理结果，我们从 19.2 秒优化到 9.8 秒，比 Linux 的 11.3 秒还要快。另外，八线程 CPU 的吞吐量达到了 Linux 的 96%，基本追平；唤醒延迟从 1042 微秒降到 8 微秒；schbench 的每秒请求数已经超过了 Linux。

**【功能广度：从零补齐的子系统】** *(约 1:10)*

性能之外，还有相当大的一块工作，是把 StarryOS 原本缺失的功能补齐。

最大的一块是显示子系统。我们从零写完了一整套 RK3588 显示驱动，包括 VOP2 显示控制器、HDMI 发送器和组合 PHY，代码全部是自己的。此前这块板子上连 `/dev/fb0` 都不存在；而现在，一个标准的 Qt6 程序可以直接显示在 HDMI 屏幕上——机器人的实时操作面板就是这么呈现的，稍后的视频里可以看到。在这一基础上，我们还把 Weston 桌面跑了起来，四种 CPU 架构都能正常通过。

为了让这些功能都能在真机上得到验证，我们还补齐了板级 I/O，覆盖相机取流、串口、USB、PWM、网络，以及 reboot 系统调用。通用兼容性方面，我们完善了进程凭证、共享内存、netlink、AF_UNIX、epoll 这些 Linux 语义，并用 PostgreSQL 完整跑通作为端到端验证。

**【创新点：把闭源 NPU 搬进仿真】** *(约 0:50)*

另一块分量很重的工作，是把 RK3588 的 NPU 搬进了仿真环境。这颗 NPU 没有公开文档，运行时是闭源二进制，以往想调驱动或调模型，只能占用一台真机。我们把它的寄存器布局、命令流水线和算子行为逆向出来，在 QEMU 里实现了一个功能级模型：它会真正执行 INT8 和浮点卷积，回写的结果与真机一致，配套了 106 个测试，还复现了三核协同的工作方式。这样一来，一块本来只能在物理板上使用的闭源加速器，就变成了可以进 CI、可以逐个算子度量的开发平台。前面提到的那个模型优化——把激活函数查表从 107 个降到 3 个——就是完全在这个仿真模型上完成的，自始至终没有碰过真机。

**【开发方法与上游贡献】** *(约 0:50)*

改动范围这么大，质量保障是我们要直接面对的问题。我们的分工方式很明确：人来定方向和做验收，AI 在几道能自动检验的关卡里反复迭代。这套流程里有四道关卡，每一道都针对不同层面的风险。最前面是 sysbench 对等性检查，保证改动之后内核的整体行为没有偏离；然后是 schbench 延迟检查，专门盯调度路径上的抖动。改动进入互审环节后，每个涉及 SMP 同步的改动都会配 7 到 26 个相互独立的评审意见，这个环节实际抓出了两个高危缺陷。最后还有一道计时正确性检查，用系统态时间占比来判断内核是否在正确的地方花时间。为了让这套流程可以无人值守地运行，我们还接了一只智能插座做带外断电——即使某次改动把内核挂死，也能通过硬断电冷启动自动恢复。所有改动最终都拆成一个个可以独立回归的 PR 回馈上游。到目前为止，我们三个人一共提交了 122 个 PR，其中 90 个已被合并。

**【收尾与演示】** *(约 0:30)*

从初赛到决赛，我们做的其实是同一件事：让 StarryOS 从能把这台机器人跑起来，一直做到和 Linux 逐项对等，其中 THP、启动时间、单核 A55 和 schbench 这几项还实现了反超；同时补齐了显示、观测、板级 I/O 在内的一大批功能，还把一颗闭源 NPU 变成了可以进 CI 的仿真模型。
